## Anatomy of build.gradle
The build file contains the configuration that tells Gradle how to build the project: for example, which external libraries the project depends on, where to download them from, and any user-defined tasks.
This is the build file from the previous example:
{% highlight kotlin %}
plugins {
    id("application")
}

group = "org.example"
version = "1.0-SNAPSHOT"

repositories {
    mavenCentral()
}

dependencies {
    testImplementation(platform("org.junit:junit-bom:6.1.3"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

application {
    mainClass.set("org.example.Main")
}

tasks.test {
    useJUnitPlatform()
}
{% endhighlight %}
Let's see the meaning of each block.
### Plugins
{% highlight kotlin %}
plugins {
    id("application")
}
{% endhighlight %}
A <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/plugins.html">Gradle plugin</a> is an extension of Gradle's core that specifies how to build and run a specific type of project, and provides ready-made tasks for it. Each programming language has its own plugins.  

In the previous section, we replaced the build file generated by IntelliJ, which used the `java` plugin, with one that uses the `application` plugin. We did it because the `application` plugin extends the `java` plugin (in other words, it inherits all of its tasks) and adds, among other things, the `run` task that, as we have seen, runs the application. As the documentation <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/java_plugin.html#java_plugin">says</a>, *"java plugin adds basic building blocks for working with JVM projects. Its feature set has been superseded by other plugins, offering more features based on your project type. Instead of applying it directly to your project, you should look into the java-library or application plugins or one of the supported alternative JVM language."*  
The <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/application_plugin.html">documentation</a> of the `application` plugin explains it in detail.  

To summarize, a plugin is just an extension of Gradle's core that adds tasks and functionality to it. More specifically, a Gradle plugin can:
1. Extend the Gradle model (for example, adding new DSL elements that can be configured).
2. Configure the project according to conventions (for example, adding new tasks).
3. Apply a specific configuration (for example, enforcing organizational standards).

### Application
{% highlight kotlin %}
application {
    mainClass.set("org.example.Main")
}
{% endhighlight %}
This block is specific to the `application` plugin. It tells Gradle that the main class of the program (i.e., its entry point) is `org.example.Main` (note that the name must be fully qualified, i.e., it must include the package). This is an example of an extension of the Gradle model.
### Group and Version
{% highlight kotlin %}
group = "org.example"
version = "1.0-SNAPSHOT"
{% endhighlight %}
These two properties identify the artifact that our project produces. The group identifies the organization or project that publishes the artifact (usually a reversed domain name), and the version identifies its release. If you look at the `build/libs` folder, you will notice that the version is part of the name of the generated `.jar` file.  

The `SNAPSHOT` suffix is a convention meaning "work in progress": the code is still under development and is not a final release yet. The group and the version are the same coordinates that we will use in a moment to identify the libraries we depend on.
### Repositories
{% highlight kotlin %}
repositories {
    mavenCentral()
}
{% endhighlight %}
Libraries are hosted in online repositories. In the <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/declaring_repositories.html">repositories</a> block, you specify which repositories Gradle should use. In our example, we use <a target="_blank" rel="noopener noreferrer" href="https://repo.maven.apache.org/maven2/">Maven Central</a>, but we can declare more than one repository. Let's see another example:
{% highlight kotlin %}
repositories {
    mavenCentral()
    google()
    maven {
        url = uri("https://repository.jboss.org/maven2")
    }
}
{% endhighlight %}
Here we have multiple repositories. If we want to fetch a library named "mickeymouse" and it does not exist in the first repository, Gradle checks the next repository in the list, and so on, until it finds it. Let's look at these repositories:
1. `mavenCentral()` is just a function that returns the URL of Maven Central.
2. `google()` is <a target="_blank" rel="noopener noreferrer" href="https://maven.google.com/web/index.html">Google's Maven repository</a>.
3. The `maven` block, with its `url` property, lets you declare a custom repository just by specifying its URL.  

These are just examples: curious readers can find more in the <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/declaring_repositories.html">official documentation</a>.
### Dependencies
{% highlight kotlin %}
dependencies {
    testImplementation(platform("org.junit:junit-bom:6.1.3"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}
{% endhighlight %}
In this block, we declare all the <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/declaring_dependencies.html#declaring-dependencies">dependencies</a> (i.e., libraries and/or frameworks) used by the project.  

Dependencies can have different scopes: some are needed to compile the source code, others only at runtime, and others only to run the tests. Look at the second line: it starts with a function, `testImplementation`. This is the configuration, i.e., the scope of the dependency. Scopes can be defined by plugins or by the user. For example, the `java` plugin defines several scopes; here are the most important ones:
1. `implementation`: dependencies used to compile and run the application (this is the most common one).
2. `compileOnly`: dependencies used only at compile time.
3. `runtimeOnly`: dependencies used only at runtime.
4. `testImplementation`: dependencies used to compile and run the tests.
5. `testRuntimeOnly`: dependencies used only when running the tests.

You can find a comprehensive explanation of the `java` plugin's scopes <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/java_plugin.html#sec:java_plugin_and_dependency_management">here</a>. Since the `application` plugin extends the `java` plugin, these scopes are available with it too. In the last part of this lesson (Example - log4j), we will see how to import a dependency and use it in our application.  

`"org.junit.jupiter:junit-jupiter"` is the dependency that we want to import. The part before the `:` is the group (i.e., an identifier of an organization, company, or project), and the part after it is the name of the dependency (in our case, `junit-jupiter`).  

A third part, after another `:`, specifies the version of the dependency. For example, the first dependency (group `org.junit`, name `junit-bom`) is bound to version `6.1.3`. It is good practice to always fix the version of a dependency. If you use a dynamic version instead (for example, `"org.junit.jupiter:junit-jupiter:latest.release"`), your next build may fetch a newer version of the library as soon as it is released, and if that version introduces breaking changes, it may break your app.  

But then, why does `junit-jupiter` have no version? Try to remove the first line (the one with `junit-bom`) and run `./gradlew test`: the build fails, because Gradle does not know which version of `junit-jupiter` to download:
{% highlight bash %}
> Could not find org.junit.jupiter:junit-jupiter:.
{% endhighlight %}
In our build file, the version comes from the first line. `junit-bom` is a special artifact called BOM (Bill of Materials): it does not contain any code, only a list of libraries (in this case, all the JUnit modules) with versions that are known to work well together. By importing it with the `platform(...)` function, we tell Gradle to take the versions of these libraries from the BOM. In this way, we write the JUnit version only once, and all the JUnit modules we use (`junit-jupiter` and `junit-platform-launcher`) are guaranteed to be compatible with each other.  

The last line, `junit-platform-launcher`, is the component that Gradle uses to discover and launch JUnit tests. It is needed only when running the tests, so it is declared as `testRuntimeOnly`. Since Gradle 9, it must be declared explicitly: if you omit it, `./gradlew test` fails with the error "Failed to load JUnit Platform".  

Finally, before adding a dependency to your project, you should always check its reliability: is it regularly updated? How many people use it? Does the publisher have a good reputation?
#### Resolving dependencies
Gradle caches the dependencies it downloads. To resolve a dependency, Gradle:
1. Looks for the artifact in the cache (usually located in `~/.gradle/caches`).  
2. If it is there, retrieves it and uses it.
3. If not, connects to the repositories specified in the `repositories` block.
4. Looks for the specific group/name/version.
5. Downloads the artifact and caches it.
6. Uses the artifact.

### Tasks
{% highlight kotlin %}
tasks.test {
    useJUnitPlatform()
}
{% endhighlight %}
This block configures the `test` task, which is provided by the Java-related plugins. We won't go into details here, but if you are interested, you can find more information <a target="_blank" rel="noopener noreferrer" href="https://docs.gradle.org/current/userguide/java_testing.html">here</a>. 

In short, our `tasks.test` block says that the project uses JUnit for testing. What is JUnit? We will answer this question in the next section.
